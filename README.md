## 2. 项目概括

本项目不是直接让大模型给客服对话打分，也不是用关键词规则做简单匹配，而是先把复杂客服指令转化为一套可执行的评估 schema，再由本地评估器对多轮对话进行高速、可解释、可追溯的结构化评估，并在少量灰区引入 LLM 进行二次仲裁。

项目命名为 **ATLAS-Eval（Atom-Traceable Local Assessment System）**。其中，**Atom-Traceable** 强调每个评估结论都能回溯到具体的评估原子、语义元素、对话原话和图表字段；**Local Assessment** 强调大规模样本评估不是逐条依赖 LLM 黑盒打分，而是在本地完成可复现的结构化验收；**System** 强调它不是单个 prompt，而是一套包含建图、编译、执行、二筛、仲裁和报告的完整评估系统。

当前 schema 的核心是“一图两表 + atom / element 语义层”：

```text
复杂客服指令
→ LLM 离线生成状态主图、知识表、限制表
→ 本地 Schema Linter / Schema Compiler
→ Atom Registry 统一抽取最小语义单元
→ Atom Transport Layer 传输 atom_id 与 atom_text
→ LLM 拆解 element 并扩张 element pool
→ 本地 Graph Evaluator 执行节点、知识、限制评分
→ 本地二筛与少量灰区 LLM 二次仲裁
→ 中文可解释评估报告
```

其中，状态主图、知识表和限制表在建图阶段保持职责分离：三者都只读取复杂指令本身，不互相读取、不互相改写。主图负责“客服有没有完成该做的对话动作和状态转移”；知识表负责“客服说出的业务事实是否正确”；限制表负责“客服是否触碰明确禁止的负向对象”。

在图表生成完成后，系统会把节点、知识和限制中的最小语义单元统一登记为 atom，并把每个 atom 拆成可本地匹配的 element 短语。这里的 atom / element 有两侧含义：图表侧的 atom / element 来自 LLM 对复杂指令的离线结构化拆解；对话侧的 atom / element 不再由 LLM 逐条生成，而是由本地 Evidence Extractor 把每轮用户和客服原话切成带有 speaker、turn_index、数字、时间、否定词和局部上下文的候选证据单元，再把图表侧 element 及其 pool 投影到这些候选证据单元上，形成“这句话命中了哪些对象、动作、事实值或违规动作”的证据账本。

因此，本文后面说“召回”时，不是指已经判定该对话正确或违规，而是指：系统先从整段对话中筛出可能与某个节点、知识或限制相关的候选证据，再在候选证据内部做更严格的 element 覆盖、事实值比较、否定方向判断或违规动作判断。也就是说，召回只是候选生成，不是最终结论。这样做的目的，是让评估不再依赖整句模板或固定关键词，而是基于“对象、动作、属性、事实值、极性、违规动作”等更细粒度的语义要素进行判断。


## 3. 方法创新点

ATLAS-Eval 的方法创新点可以归纳为三部分：第一，面向复杂指令的建图设计；第二，基于 atom 与 element 的本地语义评估召回设计；第三，LLM 与本地评估的双向合作高度集成。三者共同服务于同一个目标：让每个复杂对话评估结论都能追踪到 atom、element、候选证据和最终裁决，而不是只给出一个不可解释的黑盒分数。

### 3.1 建图设计：复杂指令到“一图两表”的可执行 schema

本项目不是直接让大模型对对话打分，而是先把复杂客服指令转化为可执行、可检查、可追溯的评估 schema。这个 schema 由 **状态主图、知识表、限制表** 组成，也就是“一图两表”。

- **状态主图**负责流程履约，判断客服有没有完成应做动作、是否按照正确顺序推进、是否根据用户状态进入正确分支、是否在需要终止时安全结束。节点只判断“动作是否完成”，不负责判断事实真假。
- **知识表**负责事实核验，判断客服说出的业务事实是否正确，例如数字、时间、金额、路径、适用场景、费用方向、系统显示状态等。只要客服说到了相关事实，本地评估器就可以用知识表核验其是否说对。
- **限制表**负责边界检查，判断客服是否越界承诺、错误保证、代替用户操作、突破系统或规则权限，或者在危险状态下继续推进。限制表不是“客服应该说什么”的正向清单，而是“客服不能做什么”的负向对象表。

三者在生成阶段保持独立：

```text
复杂指令 → 状态主图
复杂指令 → 知识表
复杂指令 → 限制表
```

也就是说，主图、知识表、限制表都只读取复杂指令本身，不把主图喂给知识表，也不把知识表喂给限制表。这样可以避免跨阶段污染：如果主图某个节点拆得不够理想，不会继续影响知识表和限制表；如果知识表抽得过细，也不会反过来改变主流程结构。

为了提升建图稳定性，系统还支持 **二次补图 / 补表**。第一次生成完成后，本地先检查结构是否存在缺项、过细、过量、字段不规范等问题；第二次只以 patch 方式补漏或修正，而不是让 LLM 重写整张图或整张表。尤其是限制表，二次补表只允许少量补充，防止模型把“不能承诺任何事”泛化成几十条硬限制，造成 hard 表爆炸。后续可以持续加强二次补图的机制，来增强图的泛化性。

这种建图设计的价值在于：它把原本混杂在长篇复杂指令中的流程、事实和限制拆成了三个职责清晰的可执行对象，使后续本地评估能够分别计算流程分、知识分、限制分，并且把每一处扣分回溯到具体节点、具体知识点或具体限制项。

### 3.2 Atom 与 Element 本地语义评估召回设计：从最小语义单元到候选精判

在“一图两表”之上，本项目进一步引入 **atom / element** 语义层。它的目的不是让图表更复杂，而是让本地 evaluator 能够用更稳定、更细粒度的方式理解真实电话对话。

**Atom** 是最小可独立评价语义单元。不同来源的 atom 含义不同：

- **node_atom**：节点下的最小履约动作，例如“确认负责人身份”“告知合同已生效”“询问发布方式”。
- **knowledge atom**：一条可核验事实，例如“标准直播延迟约 5-10 秒”“退出需前一天 18 点前取消”。
- **hard_constraint atom**：一条明确负向边界，例如“不能承诺人工改变系统结果”“不能代用户完成自助操作”。
- **soft_constraint atom**：一条整体质量要求，例如“电话表达自然”“回复简洁”。
- **activation atom**：节点或分支的触发条件，例如“用户表示不愿继续”“商家表示正在开车”。

每个 atom 都有稳定的 `atom_id`，并通过本地 Atom Transport Layer 传给 LLM。元素化阶段不再把整张图表喂给 LLM，而是只传：

```json
{
  "atom_id": "node_atom:n9:a9",
  "atom_source": "node_atom",
  "parent_id": "n9",
  "atom_text": "询问商家通过 Web 控制台、校务系统还是 SaaS 系统发课"
}
```

LLM 在这一阶段只做一件事：把 atom 的短句语义拆成 **element**，并为 element 扩展中文等价表达池。它不能改节点结构，不能改知识事实，也不能新增业务结论。

**Element** 是 atom 下用于本地匹配的短语或词，不是完整句子。一个 atom 通常拆成 2 到 5 个 element，用于表达对象、动作、属性、状态、事实值或极性。比如知识 atom：

```text
低延迟直播延迟约 1-2 秒
```

可以拆成：

```text
低延迟直播 / 延迟 / 1-2 秒
```

其中：

- `低延迟直播` 是对象主干；
- `延迟` 是属性主干；
- `1-2 秒` 是事实值。

每个 element 还有两个关键标记：

- **main**：召回主干。main 不是“看起来重要的词”，而是能区分该 atom 的最小对象或属性主干。去掉 main 后，系统就不知道这段话在谈哪个对象。
- **fact**：事实精判值。数字、时间、金额、区间、方向、极性、违规动作等通常作为 fact，用于判断“说对还是说错”。

Element 的命中机制分为三步：**候选筛选、证据成组、精判打分**。这里仍可以简称“召回”，但更准确地说，它不是把图表 atom 和对话原话做一对一相似度匹配，而是把对话原话先整理成候选证据，再判断这些证据能否支持某个图表 atom。

对话侧的候选证据由本地代码生成。系统读取 dialogue 后，会按轮次、说话人和文本切分出证据单元：用户话主要用于判断 activation / trigger，客服话主要用于判断 node_atom、knowledge 和 constraint。每个证据单元都会保留原句、标准化文本、数字和时间片段、否定词、相邻轮次窗口等信息。随后，图表侧 element 的 `value` 和 `pool` 会被投影到这些证据单元上，形成“这一句命中了哪些 element”的局部账本。这个账本就是后续节点、知识、限制判断的共同证据基础。

第一步是 **候选筛选**。系统不会直接拿完整 atom 句子和对话逐字比较，而是先用 main element 及其 pool 扫描对话。pool 是 element 的等价表达池，例如：

```text
低延迟直播 → 低延时直播 / 低延迟模式 / 低延迟直播模式
延迟 → 时延 / 延迟时间 / 延迟时长
1-2秒 → 一到两秒 / 1到2秒 / 约1至2秒
```

第二步是 **证据成组**。当一段对话命中了主要对象或属性主干后，它不会立刻被判定为完成或正确，而是进入该 atom 的候选证据池。候选池会记录它命中了哪些 main、哪些非 main、是否命中 fact、是否出现否定词，以及它来自哪一轮对话。对于客服拆句表达，系统还允许相邻客服轮次共同组成一个局部证据窗口；对于用户触发分支，系统会把多条用户 source_text 拆成多组 trigger_groups，任意一组命中即可触发对应分支。

第三步是 **精判打分**。系统只在候选证据中继续检查非 main、fact、value_check、negative/safe 等信息。这里最关键的创新细节是：**节点图、知识表和硬限制表的候选筛选顺序并不一样**，因为三者要回答的问题不同。

- **节点图的顺序是“先激活，再履约”。** 系统先看节点 activation：主线节点默认进入评估；分支、FAQ、终止节点必须先由用户 trigger_groups 或上下文状态触发。只有节点被激活后，才会继续检查该节点下的 node_atom 是否被客服话命中。这样可以避免用户没问退出、没说开车时，系统却强行扣退出 FAQ 或开车终止节点。
- **知识表的顺序是“先对象，再事实”。** 知识表不依赖某个流程节点是否激活，而是扫描客服已经说出的事实性表达。它先用 selector_groups 找到“这句话在谈哪个对象和属性”，例如“标准直播 + 延迟”或“退出飞毛腿 + 生效时间”；只有对象被召回后，才用 correct_groups、wrong_groups、fact element 和 value_check 判断说法是否正确。这样可以识别“客服流程说到了，但事实值说错了”的情况。
- **硬限制表的顺序是“先风险场景和负向对象，再看安全翻转”。** 硬限制不是正向履约清单，而是负向边界表。系统先看是否出现受保护对象、禁止动作或风险场景，例如“承诺优惠券”“站长干预排名”“用户开车仍继续介绍”；再检查客服是否使用了 safe_groups 中的安全表达，例如“不承诺结果，以系统规则为准”“您在开车的话我稍后再打”。因此硬限制不是从正确事实召回，而是从违规风险召回。

这种不同顺序是本项目的细节创新之一。节点图解决“该不该评这个动作、动作有没有完成”；知识表解决“说到这个事实时是否说对”；硬限制表解决“是否碰到明确禁止的负向对象”。三者都使用 element，但召回路径不同，避免把流程缺失、事实错误和违规承诺混成一种问题。

这套机制的巧妙之处在于，它把传统的整句匹配拆成了更可控的 **候选筛选 → 证据成组 → 事实 / 违规精判**。main 保证候选筛选稳定性，pool 覆盖真实口语变体，fact 和 value_check 保证事实不被说错，negative/safe 区分违规承诺和合规说明。这样既避免了关键词匹配的粗糙误判，也避免了把每条对话都交给 LLM 打分带来的高成本和不可控性。

### 3.3 LLM 与本地评估双向合作高度集成：离线生成、在线编译、本地执行、灰区仲裁

本项目没有把 LLM 当成逐条对话评分器，而是把 LLM 和本地系统拆成两个互相配合的角色。

LLM 主要负责 **离线结构生成**：根据复杂指令生成状态主图、知识表、限制表，并在 atom 传输层上完成 element 拆解和 pool 扩张。这部分是离线或低频执行的，虽然一次完整建图可能耗时较长，但它不是每条对话都要重复调用。

本地系统主要负责 **编译、执行和治理**：

- Schema Linter 检查图表是否存在明显结构问题、缺失关系、空终止节点、过宽证据组等；
- Schema Compiler 统一字段、ID、relation group、atom、element、value_check、hard/soft 表结构；
- Graph Evaluator 在本地完成节点、关系、知识、限制的批量评分；
- 本地 guard 检查硬编码、负包泄漏、非法 JSON、中文语境、限制表爆炸等问题；
- 报告生成器把每个样本的命中、未命中、冲突和归因输出为中文报告。

这种合作是双向的。一方面，本地系统会把复杂指令组织成更适合 LLM 生成的阶段化 prompt，并在主图、知识表、限制表、元素化、元素扩张之间控制输入边界，防止模型任务混乱；另一方面，LLM 生成的结果不会被直接信任，而是会被本地系统编译、规范化、裁剪和检查，只有符合方法契约的图表才会进入评估。

在评估阶段，大规模样本主要由本地 evaluator 直接完成。只有当本地证据显示“语义相近但证据不足”“是否违规存在歧义”“候选事实无法稳定判断”等灰区情况时，系统才会把经过本地压缩后的局部信息交给 LLM 二次仲裁。这里不是把所有 review 项都交给模型，而是先生成灰区仲裁候选，再由本地二次筛选模块按 schema 锚点、证据强度、重复度、同证据账本关系和优先级进行过滤、合并和降噪。报告中可以看到，经过二筛后，通常只有约三分之一的高价值候选会进入真正的仲裁区，其余候选会保留在本地审计账本中，不消耗在线推理成本。

这个机制还具有随数据集增大而增强的特点：样本越多，重复候选、同类证据、同一 schema 锚点下的相似灰区就越容易被本地合并；真正需要 LLM 处理的不是样本数量本身，而是少量无法由本地结构稳定判断的语义边界。因此，数据规模扩大时，本地二筛的压缩和合并能力会更明显，LLM 仲裁不会线性膨胀。

因此，本项目的整体架构可以概括为：

```text
LLM 离线建图与元素化
→ 本地编译、治理与高速评估
→ 本地发现灰区
→ LLM 少量仲裁
→ 本地合并裁决并生成中文可解释报告
```

这种高度集成的优势在于：既利用了 LLM 理解复杂指令和生成语义结构的能力，又保留了本地评估的速度、稳定性、可复现性和可解释性。对于工业客服质检场景来说，真正昂贵的语义推理被前置到离线建图和少量仲裁中，而大量日常对话评估则可以在本地快速完成。

因此，ATLAS-Eval 这个名字对应的是一套完整方法闭环：**Atom** 表示评估对象被拆成可追踪原子，**Traceable** 表示命中、缺失、冲突和违规都能回到证据账本，**Local** 表示主体评分在本地执行，**Assessment System** 表示它同时包含建图、编译、评估、仲裁和报告，而不是单一模型调用。

- 九成以上样本主要依靠本地机制直接通过；
- 其他灰区样本可以通过二次仲裁完成局部协调；
- 本地机制仍然是评估主线，LLM 仲裁只作为灰区补充。

调试和演示时，状态图一般是离线预先生成的。一次完整建图通常需要 5 到 10 分钟不等；二次仲裁经过本地过滤筛选后，通常可以控制在 1 分钟以内。实际用时会受到网络、模型响应速度、样本数量和仲裁模式影响。

## 5. 如何从零运行项目

本节用于帮助评委老师或第一次接触项目的同学，从一个刚解压的项目包开始，完整跑通环境配置、离线图评估 demo、在线建图评估和结果查看。

### 5.1 创建虚拟环境并安装依赖

进入项目根目录后，先创建 Python 虚拟环境。

Windows PowerShell：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Linux / macOS：

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

`.venv/` 在项目中只保留占位文件，不包含真实环境。这样做是为了让项目结构清晰，同时避免把本地虚拟环境打包进仓库。

### 5.2 设置 LLM 参数

如果只想查看离线图评估流程，并且关闭二级判断，可以不设置 API Key，直接使用已经保留在 `example/` 中的离线示例图。

如果需要运行在线建图，或者在评估灰区样本时开启 LLM 二次仲裁，需要设置 LLM 参数。项目不在 README 中绑定具体模型名，运行时请根据实际使用的平台填写 API Key、Base URL 和模型名称。

Windows PowerShell：

```powershell
$env:LLM_API_KEY="你的 LLM API Key"
$env:LLM_BASE_URL="你的 LLM BASE URL"
$env:LLM_MODEL="你的LLM NAME"
```

Linux / macOS：

```bash
export LLM_API_KEY="你的 LLM API Key"
export LLM_BASE_URL="你的 LLM BASE URL"
export LLM_MODEL="你的LLM NAME"
```

API Key 只应放在本地环境变量或界面输入框中，不要写入代码、配置文件、评估报告或压缩包。

### 5.3 运行离线图评估 demo

离线图评估适合比赛展示和复现实验结果。它不会重新调用 LLM 建图，而是直接读取项目中已有的 `graph.json`，再对 `data/dialogues` 中的对话样本进行本地评估，并在需要时开启少量二次仲裁。

图形界面运行方式：

```bash
python app_offline.py
```

在界面中选择已有离线图、对话数据目录、正包或负包，并选择二级判断模式。为了稳定复现展示效果，推荐优先使用 `app_offline.py`。

也可以使用命令行快速验证商家包：

```bash
PYTHONPATH=src python scripts/run_offline_graph.py \
  --graph example/merchant_graph_example.json \
  --dialogues data/dialogues \
  --pack all \
  --llm-mode off
```

命令行快速验证骑手包：

```bash
PYTHONPATH=src python scripts/run_offline_graph.py \
  --graph example/rider_graph_example.json \
  --dialogues data/dialogues \
  --pack all \
  --llm-mode off
```

其中：

- `--graph` 指定要使用的离线状态图；
- `--dialogues` 指定对话数据目录；
- `--pack all` 表示同时评估正包和负包；
- `--llm-mode off` 表示关闭二次仲裁，只查看纯本地评估结果。

如果希望查看 LLM 二次仲裁效果，可以在图形界面中选择辅助模式，或在命令行中按实际配置打开对应的 LLM 模式。

### 5.4 运行在线建图 + 评估

如果需要展示从复杂指令到状态图再到评估报告的完整链路，可以运行：

```bash
python app.py
```

该模式会执行：

```text
输入复杂客服指令
→ LLM 独立生成主图、知识表、限制表
→ 二次补图 / 补表与本地结构治理
→ Atom Registry 与 Element 语义扩张
→ 本地 Schema Linter / Schema Compiler
→ 读取对话数据
→ 本地 Graph Evaluator 评估
→ 可选 LLM 二次仲裁
→ 生成中文可解释报告
```

在界面中粘贴复杂客服指令，填写 LLM API Key，选择建图模式、评估数据包和二级判断模式。系统会把运行产物写入类似下面的目录：

```text
runs/llm_latest__时间戳/
```

在线建图模式会额外统计 LLM 建图 tokens、建图用时、评估用时和二次仲裁 tokens，因此更适合展示系统完整能力；离线图评估模式则更适合稳定复现已有结果。

### 5.5 查看运行输出

一次运行结束后，重点查看以下文件：

| 文件 | 说明 |
| --- | --- |
| `report.html` | 当前选择的报告入口。 |
| `report_simple.html` | 面向评委的简版结果报告，重点展示总分、通过情况和主要归因。 |
| `report_detail.html` | 面向技术评审的详细过程报告，展示节点、知识、限制、证据和仲裁过程。 |
| `all_reports_merged.json` | 所有样本的结构化评估明细。 |
| `graph.json` | 本次使用或生成的状态图。 |
| `run_manifest.json` | 本次运行索引，记录输入、输出和关键路径。 |
| `run_token_usage.json` | LLM 调用次数和 token 统计。 |
| `run_timing_summary.json` | LLM 建图、本地评估、二次仲裁等耗时统计。 |

GitHub 清洁包默认清空 `runs/`，因此不会预置历史运行报告。可以使用以下离线示例图重新生成报告：


这两份 example 图适合配合 `app_offline.py` 或 `scripts/run_offline_graph.py` 快速复现中文可解释报告效果。

## 6. 数据集说明

当前本地数据集主要围绕赛题给出的两类复杂客服指令构建：

1. **飞毛腿骑手合同生效通知与提醒**
2. **商家直播课程发布能力升级告知**

数据集包含正包和负包。正包用于验证系统能否识别流程完整、知识正确、限制合规的客服对话；负包用于验证系统能否识别流程缺失、知识错误、限制违规、异常终止处理不当等问题。

本地数据集目前主要针对上述两大题目组所给指令设计。如需引入其他业务数据，读取数据集的接口和样本组织方式后续可以进一步扩展。由于比赛时间有限，当前版本保留了围绕两类核心任务的设计。详细介绍可见 `docs/04_DATASET_DESIGN.md`。

## 7. 无硬编码与无泄漏说明

为了给 LLM 建图留下保底机制，本地存在少量通用话术编码，例如“不方便”“稍后”“以规则为准”“不能承诺”等跨业务客服表达。这类内容不绑定具体业务事实，主要用于增强通用语义匹配能力。

但项目拒绝针对具体业务添加业务话术硬编码，例如不把“飞毛腿”“骑手合同”“标准直播”“低延迟直播”“派单”“费用优惠”等具体业务词写在 evaluator 里。业务事实必须来自 LLM 生成的 graph/schema，而不是由代码提前作弊式写入。

同时，负包中的 `wrong_statement`、`evidence_span` 等标注信息不能被编译成判分答案，避免负包泄漏。项目内自带硬编码检测和负包泄漏自查工具，用于确保泛化性和结果的非作弊性：

```bash
PYTHONPATH=src python tools/hardcode_guard.py
PYTHONPATH=src python tools/anti_leak_guard.py
PYTHONPATH=src python tools/negative_purity_check.py data/dialogues/negative_pack
```
