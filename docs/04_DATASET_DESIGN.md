# 04 数据集构成与多样性说明

本文档面向评审说明 ATLAS-Eval 数据集的构成方式、覆盖维度、正负样本设计逻辑，以及数据集如何支撑复杂指令多轮对话评估。数据集围绕两类中文客服任务构建：

- 商家课程发布页直播升级通知；
- 飞毛腿骑手合同生效通知与配送提醒。

为保持中文语境，本文使用“正包”“负包”“流程缺失”“知识错误”“限制违规”“误杀控制”等表述。必要时保留代码字段，例如 `injected_errors`、`wrong_statement`、`evidence_span`、`expected_detector`，用于说明数据格式和反泄漏边界。

---

## 1. 数据集规模与目录结构

数据集只保留对话样本本体，不依赖报告、运行缓存、聚合 json 或中间工作文件。目录结构如下：

```text
dialogues/
├── positive/
│   ├── rider/
│   │   ├── ridder_positive_00.json
│   │   └── ...
│   └── merchant/
│       ├── merchant_positive_00.json
│       └── ...
└── negative/
    ├── rider/
    │   ├── rider_negative_00_01.json
    │   └── ...
    └── merchant/
        ├── merchant_negative_00_01.json
        └── ...
```

数量如下：

| 业务域 | 正包数量 | 负包数量 | 合计 |
| --- | ---: | ---: | ---: |
| 骑手飞毛腿合同通知 | 31 | 60 | 91 |
| 商家直播产品升级通知 | 31 | 60 | 91 |
| 总计 | 62 | 120 | 182 |

命名规则如下：

| 类型 | 命名规则 | 说明 |
| --- | --- | --- |
| 骑手正包 | `ridder_positive_00` ~ `ridder_positive_30` | 沿用项目数据中的 `ridder` 拼法，保证脚本读取稳定。 |
| 商家正包 | `merchant_positive_00` ~ `merchant_positive_30` | 覆盖商家直播升级任务的合规对话。 |
| 骑手负包 | `rider_negative_00_01` ~ `rider_negative_00_60` | `00` 表示对齐标准任务结构，后两位为负例编号。 |
| 商家负包 | `merchant_negative_00_01` ~ `merchant_negative_00_60` | 与骑手负包保持同样编号体系。 |

## 2. 数据集在 ATLAS-Eval 方法中的作用

ATLAS-Eval 不是简单判断一段话“像不像客服”，而是验证客服是否真正执行复杂指令。数据集用于检验三类能力：

```text
正包：合格客服对话能否通过。
负包：预设错误能否被识别。
误杀控制：负包中无关正确部分是否不会被乱扣。
```

因此，数据集的设计重点不只是“负包能不能被打下来”，还包括：

- 正包是否能在自然表达、分支触发、顺序变化下通过；
- 负包是否只在预设错误处被扣分；
- 未触发 FAQ、未触发分支、被终止策略压制的节点是否不会被误判为缺失；
- 知识错误是否能被知识表稳定识别；
- 明确限制违规是否能被限制表定位；
- 报告是否能把错误归因到具体对话句子、图表对象和评估原子。

这种设计让数据集既能测试评分结果，也能测试评估过程的可解释性。

### 2.1 数据集如何检验 DialogueAtom 建模

数据集不只是在测试图表 atom 是否覆盖完整，也在测试真实对话侧的 **DialogueAtom** 建模是否稳定。运行时，系统不会把一整段客服话直接拿去和图表模板比较，而是先把 `turns` 转成 `EvidenceUnit`，再按说话人、标点、逗号、转折词、并列词和相邻话轮切成多个局部 `DialogueAtom`。

每个 `DialogueAtom` 会保留原始文本、轮次、说话人和局部片段，并补充一组通用 elements，例如 `speaker_role=user/assistant`、问句、确认、忙碌、不方便、开车、拒绝、结束、继续推进等。这些通用 elements 只描述中文客服对话里的通用话语行为，不包含骑手或商家的业务答案。

真正的业务语义来自图表侧 atom。状态图、知识表和限制表中的图表 atom 会先被拆成 `main / fact / pool`：

```text
main：负责召回候选 DialogueAtom
fact：负责数字、时间、金额、方向、极性等事实精判
pool：负责严格等价表达，例如口语变体、同义短语和格式等价
```

因此，评估时的顺序更准确地说是：

```text
真实对话 → EvidenceUnit → DialogueAtom → 通用 elements
图表 atom → main/fact/pool
图表 main + pool 先召回候选 DialogueAtom
候选窗口内再检查 value / aliases / pool / fact
最终形成 hit / review / miss
```

这也解释了为什么数据集要保留自然拆句、用户先提供状态、FAQ 分散追问和轻微顺序变化：这些样本不是单纯增加语言多样性，而是在检验系统能否先把真实对话切成可用的 DialogueAtom，再由图表 atom 的 main 和 pool 召回候选，最后在候选内完成元素级精判。

## 3. 正包设计

正包用于测试评估器是否能认可合格客服表现。正包不是模板答案，而是在保证核心事实正确、流程合规的前提下，覆盖真实电话沟通中的不同用户状态。

### 3.1 正包共同要求

正包一般满足：

- 主线流程完整；
- 用户触发分支后能按需回应；
- FAQ 只在用户问到时回答，不强行展开所有知识；
- 业务事实正确；
- 不越界承诺；
- 用户忙碌、开车、拒绝或无法继续时能合理收束；
- 客服话术保持规章化和电话自然感，允许拆句和轻微顺序变化。

评估器根据激活子图判断样本，不要求未触发 FAQ 全部出现。因此，一个合格正包不需要机械讲完所有知识，只需要完成对话语境中被激活的节点和评估原子。

### 3.2 正包多样性

正包覆盖以下用户表达类型：

```text
配合确认
理性追问
焦虑担心
强势要求讲重点
急躁打断
质疑口径
忙碌不方便
开车需要终止
反复追问同一规则
边界试探
```

这些样本用于测试系统是否能从自然中文话术中识别触发条件，而不是只依赖固定关键词。

### 3.3 终止型正包不是流程缺失

正包中特意包含终止型对话。例如：

- 骑手正在骑车，客服应暂停业务推进，稍后联系；
- 商家正在开车，客服应礼貌表示稍后再打；
- 骑手明确无法配送，客服应安慰收束，而不是继续施压；
- 用户不方便继续沟通，客服应压缩或终止，而不是强行把全部流程讲完。

这些样本看起来没有覆盖全部主线，但它们不是错误样本。因为用户状态触发了更高优先级的安全或终止策略。数据集通过这类样本检验评估器能否区分“合理终止”和“流程缺失”。

## 4. 负包设计

负包不是随机写差，而是在整体自然、上下文顺滑的基础上注入明确错误。负包要求错误可解释、可定位、可验收，避免把一条样本写成“整段都错”。

### 4.1 错误族

| 错误族 | 中文含义 | 主要检测模块 |
| --- | --- | --- |
| `flow_missing` | 激活节点或激活原子没有完成。 | 综合评估器 + 正负包验收。 |
| `knowledge_violation` | 客服说法与知识表事实冲突。 | 知识表核验。 |
| `constraint_violation` | 客服越界承诺、违规推进或突破硬限制。 | 限制表核验。 |
| `context_transition_error` | 忙碌、开车、拒绝等上下文处理不当。 | 综合评估器 + 限制表核验。 |

### 4.2 流程缺失

流程缺失样本关注“该说的没说”。例如：

- 没有确认身份；
- 没有询问能否开始配送；
- 没有说明后台临时走低延迟的原因；
- 没有引导第三方系统开通路径；
- 没有确认学员端费用；
- 没有说明企业微信跟进。

流程缺失不是简单删句，而是把上下文改写得自然，让它像真实客服遗漏，而不是模板被截断。

### 4.3 知识错误

知识错误是数据集的重要组成部分。它直接对齐知识表，适合测试系统对数值、时间、入口、费用方向、适用场景和条件关系的判断能力。

骑手侧常见知识错误包括：

- 单日合同 12 单说成 10 单或 8 单；
- 多日合同每天 10 单说成每天 8 单；
- 连续 7 天说成连续 5 天；
- 前一天 18 点前取消说成 20 点前或当天 24 点前；
- App 飞毛腿报名入口说成订单页；
- 取消后次日生效说成当天生效；
- 恶劣天气订单量通常更高说成订单更少；
- 拒单、取消、超时影响排名资格说成不影响；
- 每单多 1.5 元说成 3 元。

商家侧常见知识错误包括：

- 标准直播 5 到 10 秒说成 1 到 2 秒；
- 低延迟直播 1 到 2 秒说成 5 到 10 秒；
- 低延迟费用略高说成费用更低或相同；
- 标准直播适合大班课说成不适合大班课；
- 低延迟适合小班课/实操课说成不适合；
- 第三方系统路径说错；
- 学员端费用入口说错；
- 原费用是否适用需要确认说成不用确认；
- 发布页两个选项说成只有低延迟一个选项。

### 4.4 限制违规

限制违规只保留能从复杂指令和限制表直接读出的明确边界。数据集不把所有客服常识都当成硬限制，而是重点测试明确负向对象。

商家侧主要覆盖：

- 商家开车时仍继续推进后台操作；
- 承诺折扣券或优惠券；
- 使用明确禁用的语气词，例如“嘿嘿”“嘻嘻”；
- 在用户明确不适合继续沟通时仍强行推进核心流程。

骑手侧也保留若干明确限制违规样本，主要覆盖：

- 声称站长可以干预排名或保留名额；
- 涉及退出时由站长代为取消或越权处理；
- 恶劣天气、身体不适、骑车等危险或不方便状态下仍继续施压；
- 骑手已明确不适合继续听电话时仍推进合同或单量说明。

这类样本的共同特点是：违规点不是泛泛的“态度不好”，而是可以落到限制表中的负向对象、禁止动作或安全终止边界。

### 4.5 复合错误

复合错误指一条对话中同时存在两个或三个明确错误。例如：

- 流程缺失 + 知识错误；
- 知识错误 + 知识错误；
- 流程缺失 + 知识错误 + 明确限制违规。

复合负包不是为了增加难度而堆错，而是测试系统能否在自然多轮对话中定位多个错误。每个错误都必须能独立解释，并且能够对应到图表中的节点、知识项或限制项。

## 5. 商家数据覆盖

商家任务核心是课程发布页直播能力升级告知。

### 5.1 主流程

| 测试点 | 说明 |
| --- | --- |
| 身份确认 | 确认对方是否为负责人，非负责人请转达。 |
| 是否知情 | 询问商家是否知道后台已走低延迟线路。 |
| 临时开启原因 | 不知情时说明前端未开放、为保障音视频与白板同步而临时开启。 |
| 升级内容 | 说明发布页新增标准直播和低延迟直播两个独立选项。 |
| 直播区别 | 标准直播费用较低、延迟较高；低延迟直播互动更流畅、费用略高。 |
| 发布方式 | 确认或根据用户已提供信息获取 Web/第三方系统方式。 |
| 费用设置 | 确认或根据用户已提供信息判断学员端费用是否适用低延迟直播。 |
| 企业微信 | 确认当前号码是否可添加企业微信并说明后续验证。 |
| 结束 | 礼貌收束。 |

### 5.2 条件分支

| 分支 | 正确处理 |
| --- | --- |
| Web 控制台已显示 | 告知可直接使用。 |
| Web 控制台未显示 | 后台配置并请明天查看。 |
| 第三方系统已显示 | 告知按需选择。 |
| 第三方系统未显示 | 引导进入“我的 / 服务商管理 / 直播平台 / 服务产品”开通。 |
| 已设置费用 | 提醒低延迟直播也应适用该费用。 |
| 无法配置费用 | 引导设置直播线路附加费。 |
| 号码可添加企微 | 告知稍后添加并请通过验证。 |
| 号码不可添加企微 | 请提供可添加手机号，再发送验证提示。 |
| 忙碌 | 简短说明后继续核心内容。 |
| 开车 | 稍后再打并终止，不继续推进。 |

### 5.3 商家知识重点

```text
标准直播/低延迟直播的延迟、费用、适用场景
后台已走低延迟线路的原因
第三方系统开通路径
费用适用关系
企业微信添加方式
```

### 5.4 商家限制重点

```text
禁用明确话术
禁止承诺折扣券或优惠券
用户开车时不得继续推进
不得把低延迟直播说成唯一选择
不得跳过学员端费用确认
```

商家侧的限制样本围绕明确指令边界设计，不依赖额外平台权限常识。典型负包包括：商家正在开车时客服仍要求查看后台、客服承诺优惠券或折扣券、客服使用明确禁用语气词。

## 6. 骑手数据覆盖

骑手任务核心是通知飞毛腿合同生效、确认配送意愿、说明规则并处理追问。

### 6.1 主流程

| 测试点 | 说明 |
| --- | --- |
| 身份确认 | 确认是否为李师傅，并表明站长身份。 |
| 合同生效 | 告知今天飞毛腿合同已签署并生效。 |
| 能否配送 | 询问是否可以开始配送。 |
| 必要规则 | 说明单日、多日、排名、退出、奖励等关键规则。 |
| 配送意愿分支 | 可以配送则提醒规则和安全；不想配送则适度挽留；坚持无法配送则安慰收束。 |

### 6.2 FAQ 与分支

| 分支 | 正确处理 |
| --- | --- |
| 单日合同单量 | 说明当天至少完成 12 单。 |
| 多日合同单量 | 说明每天至少完成 10 单。 |
| 连续天数 | 说明连续 7 天配送与奖励条件相关。 |
| 退出飞毛腿 | 说明前一天 18 点前在 App 飞毛腿报名里取消，次日生效。 |
| 额外奖励 | 说明连续 7 天每天 10 单才有额外奖励，每单多 1.5 元。 |
| 排名/名额 | 说明飞毛腿报名按排名进行，不是站长人工干预。 |
| 恶劣天气/订单量 | 说明在安全前提下，订单量通常更高，按规则完成有助于资格。 |
| 超职责问题 | 说明向同事确认后回电，能回答的先回答。 |

### 6.3 骑手知识重点

```text
合同生效时间
单日合同单量
多日合同每日单量
连续配送天数
退出截止时间和生效时间
退出入口
额外奖励条件
额外奖励金额
排名非站长干预
拒单、取消、超时对资格的影响
恶劣天气和订单量对资格帮助
```

### 6.4 骑手限制重点

```text
站长不得声称可干预排名或保留名额
涉及退出时不得代骑手操作或越权处理
配送安全优先
骑车、开车、身体不适或明显不方便时不继续推进
坚持无法配送后应安慰收束
职责范围外问题不编造答案
```

骑手样本仍以流程和知识错误为主体，同时保留一组明确限制违规，用于测试限制表对负向对象的识别能力。典型违规包括：客服声称可以后台调整排名或保住名额、替骑手取消飞毛腿、雨大或身体不适时仍要求先完成单量、骑手正在骑车时仍继续讲合同要求。

## 7. 数据集与评估逻辑的对应关系

| 数据集设计 | 评估器对应机制 |
| --- | --- |
| 用户自然表达多样 | 用户说法扩张与多组触发元素。 |
| FAQ 分散追问 | FAQ 原子路由，只评用户问到的对象。 |
| 用户已提供状态 | 信息获取原子支持“用户已提供即可满足”。 |
| 知识错误 | 对象召回 + 错误事实组 + 数值校验 + 方向冲突。 |
| 限制违规 | 硬限制违规组 / 安全组；骑手侧重点覆盖站长干预、代为取消、安全终止，商家侧重点覆盖优惠承诺、开车推进、禁用语气词。 |
| 忙碌、开车、拒绝 | 终止策略和上下文转场。 |
| 负包局部错误 | 预设错误命中 + 额外误杀控制。 |

数据集设计遵循一个原则：负包尽量落在图表可执行对象上，流程错误对应状态主图，事实错误对应知识表，限制错误对应明确硬边界。

## 8. `injected_errors` 与反泄漏边界

负包中保留 `injected_errors` 字段，用于说明该样本被人为注入了什么错误。它主要用于数据集验收、报告解释和人工复查，不允许被评估器直接读取为判分答案。

常见字段包括：

| 字段 | 含义 |
| --- | --- |
| `error_family` | 错误类型，例如 `flow_missing`、`knowledge_violation`、`constraint_violation`。 |
| `target_id` | 错误对应的图表目标。 |
| `wrong_statement` | 客服实际说出的错误句。 |
| `evidence_span` | 与错误句对应的原文片段。 |
| `description` | 为什么这句话构成错误。 |
| `expected_detector` | 预期由哪个模块识别，例如 `schema_executor`、`knowledge_judge` 或 `constraint_judge`。 |

反泄漏边界如下：

```text
injected_errors 可用于验收对齐和报告解释；
wrong_statement 可用于人工复查；
evidence_span 可用于定位错误原文；
这些字段不能进入图编译，也不能成为本地评分规则。
```

这样可以保证负包标签不会泄漏到 evaluator，同时又保留可解释性。

## 9. 数据集质量控制

### 9.1 正包质量控制

正包检查重点：

- 是否完整覆盖被激活主线；
- 是否存在知识错误；
- 是否存在越界承诺；
- 是否把终止场景错误地继续推进；
- 是否因表达过度简略导致关键原子无法命中；
- 骑手样本是否先确认“是不是李师傅”；
- 商家样本是否先确认负责人身份或处理转达情况；
- 是否保持电话客服语境下的自然短句。

### 9.2 负包质量控制

负包检查重点：

- 每条负包是否有明确错误目标；
- 单点负包是否只注入一个主要错误；
- 复合负包中的每个错误是否能独立解释；
- `wrong_statement` 和 `evidence_span` 是否能在 `turns` 中逐字找到；
- 负包其他无关部分是否仍然合规；
- 错误是否能对应到状态主图、知识表或限制表；
- 是否避免使用超出复杂指令本身的凭空难题。

其中，骑手限制违规样本必须能够对应到限制表中的清晰对象：排名/名额是否可由站长干预、退出是否可由站长代操作、危险或不方便状态下是否应停止推进。不能为了制造负包而加入“私下补贴、抹掉记录、后台改履约结果”等难以从指令直接读出的内容。

### 9.3 负包纯度控制

负包纯度不是指“整段对话越差越好”，而是指错误目标清楚、无关内容干净。例如：

```text
流程缺失负包：只缺对应流程，其他知识不乱错。
知识错误负包：只说错对应事实，其他流程不乱漏。
限制违规负包：只触发明确边界，不附带大量无关错误。
复合负包：错误数量可控，每个错误都能单独归因。
```

这种设计能减少误杀，使报告更容易解释。

## 10. 数据集的工业可用性

本数据集具有较强的工程应用价值。

第一，它贴近真实客服电话。用户不总是顺序配合，而会出现忙碌、疑惑、焦虑、质疑、价格敏感、规则混淆、场景选择等自然状态。

第二，它的错误是可解释的。每条负包都能说明错在哪里、错在流程、知识还是限制，并能定位到具体客服原话。

第三，它适合低成本评估。复杂指令先离线建成图和表，正式验收时主要由本地评估器执行，只有局部灰区才需要 LLM 仲裁。

第四，它能防止模型只学会模板答案。正包存在自然拆句、用户先提供状态、FAQ 分散追问、终止策略等情况，能测试系统是否真正理解激活子图，而不是只做关键词覆盖。

---

## 11. 可扩展方向

数据集仍可继续扩展，但扩展时应保持以下原则：

1. 每条负包只注入一到两个主要错误，避免归因不清；
2. 正包可以增加自然拆句和用户先提供状态，但不能漏掉关键事实；
3. 负包预设错误必须对应到图表中的节点、评估原子、知识项或硬限制；
4. 不设计只能靠客服常识判断、复杂指令中没有依据的负包；
5. 触发条件要清楚，避免用户话术模糊到无法判断该不该评分；
6. 业务事实仍应来自复杂指令，不写进本地评估代码。

---

## 12. 一句话总结

本数据集包含骑手与商家两个业务域，各 31 条正包、60 条负包。正包用于验证自然合规履约，负包用于验证流程缺失、知识错误和明确限制违规。数据集的核心价值不在于堆砌极端错误，而在于把复杂指令拆成可验证的流程对象、知识对象和边界对象，从而为 ATLAS-Eval 的“图表 atom + DialogueAtom”双侧建模提供稳定、可解释、可复现的验收基础。
