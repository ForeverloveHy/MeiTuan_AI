# 03 双案例样本走读：沿评估流水线理解 ATLAS-Eval 如何判断

本文档用两个案例说明当前 ATLAS-Eval 如何从原始对话走到报告结论。为保持中文语境，本文尽量使用中文术语：评估原子、语义元素、触发话术、激活子图、知识核验、限制核验。必要时在括号中保留代码字段，例如 `atom`、`element_groups`、`trigger_groups`。

两个案例分别展示：

| 案例 | 错误族 | 说明 |
| --- | --- | --- |
| 案例一 | 流程缺失 | 用户触发了一个明确问题，但客服没有完成对应激活原子。 |
| 案例二 | 限制违规 | 客服回应了问题，但说法越过硬限制边界。 |

---

## 1. 当前评估流水线

一条样本进入系统后，处理顺序为：

```text
读取对话
→ 抽取证据单元 EvidenceUnit
→ 切分为 DialogueAtom 并补充通用 elements
→ 图表 trigger/main/pool 召回候选 DialogueAtom
→ 用户话命中触发元素组
→ 形成激活子图
→ 客服话匹配流程原子的语义元素组
→ 知识表核验事实正确性
→ 限制表核验边界合规性
→ 综合节点、关系、上下文、知识和限制
→ 正负包验收
→ 本地二筛与可选 LLM 仲裁
→ 报告解释
```

用户话主要用于触发节点；客服话主要用于完成流程、支持或冲突知识事实、触发或避免限制违规。

在报告链路中，真实对话不会直接和整句模板比较。系统会先把每轮话切成 `DialogueAtom`：整轮文本保留一份，同时按逗号、句号、问号、分号和“然后、另外、还有”等连接词切出局部子句。每个 DialogueAtom 会带上 speaker、turn_index、text，并补充“问句、确认、开车、忙碌、拒绝、结束、继续推进”等通用 elements。随后，图表 atom 的 main element 与 pool 先召回候选 DialogueAtom；只有进入候选池后，系统才继续检查 fact、negative/safe、value_check 和完整 element 覆盖率。

## 2. 案例一：流程缺失如何被定位

### 2.1 样本意图

假设用户问：

```text
高峰要上线吗？
```

或：

```text
这个费用怎么确认？
```

这类问题在图中会对应一个用户触发节点，例如 FAQ 节点或条件分支节点。负包故意让客服没有回答该问题，而是转移话题或只讲其他规则。

### 2.2 用户触发如何发生

建图阶段会为该节点生成多条用户可能说法。每条用户说法会被拆成一组触发元素。

例如：

```json
{
  "source_text": "高峰要上线吗",
  "elements": [
    {"value": "高峰", "main": true},
    {"value": "上线", "main": true}
  ]
}
```

再如：

```json
{
  "source_text": "费用这块已经设置了吗",
  "elements": [
    {"value": "费用", "main": true},
    {"value": "设置", "main": true}
  ]
}
```

用户原话命中任一触发元素组后，对应节点和相关评估原子被激活。

### 2.3 激活原子如何判断完成

假设被激活的客服侧评估原子是：

```text
说明午餐、晚餐高峰期需要上线
```

它的语义元素组可以是：

```json
[
  {"value": "午餐高峰", "main": true, "pool": ["午高峰", "中午高峰"]},
  {"value": "晚餐高峰", "main": true, "pool": ["晚高峰", "晚上高峰"]},
  {"value": "需要上线", "main": true, "pool": ["要上线", "保持在线"]}
]
```

正包客服如果说：

```text
午餐和晚餐高峰期需要上线，这两个时间段比较关键。
```

则客服话命中该评估原子。负包客服如果说：

```text
这个后面你自己看页面，我先说其他规则。
```

则没有命中关键元素，该激活原子缺失。

### 2.4 激活子图如何避免误杀

如果用户只问“高峰上线”，系统只评分高峰上线相关原子，不会同时要求客服回答退出、奖励、排名、费用、企业微信等其他问题。

这就是当前版本相对旧版的重要变化：

```text
不是整张 FAQ 图一起扣分，
而是用户问什么，激活什么，评分什么。
```

如果某个 FAQ 节点内部包含多个问题对象，本地评估器也会尽量按问题对象路由，只评用户实际问到的那一类。

### 2.5 知识和限制为什么不乱扣

这条负包只缺流程。如果客服说出的其他事实都正确，知识表不应产生冲突；如果客服没有越界承诺，限制表也不应产生违规。

最终报告会把错误归因到：

```text
激活节点 / 激活原子缺失
```

而不是泛泛说“回答不好”。

### 2.6 负包验收

负包通过的含义不是客服合格，而是系统成功识别了预设错误。对于流程缺失负包，验收逻辑是：

```text
预设错误是流程缺失
→ 对应节点或评估原子被激活
→ 客服没有完成该原子
→ 本地评估器产生流程缺失事件
→ 负包预设错误命中
```

同时，系统还会检查额外误杀。如果因为触发过宽导致大量无关节点也被扣分，负包会被判为误杀过多，而不是直接算好结果。

## 3. 案例二：限制违规如何被定位

### 3.1 样本意图

用户问排名、名额、优惠、系统显示、开车等边界问题。客服在流程上可能回应了问题，但说出了禁止内容，例如：

```text
我帮你协调排名。
我保证给你优惠券。
你开车也没关系，我先讲完。
```

这些问题由硬限制表判断。

### 3.2 硬限制如何定义违规

一条硬限制通常包含三类内容：

```text
触发场景：什么时候需要关注这条限制。
违规组：受保护对象 + 禁止动作。
安全组：同一对象下的安全说法。
```

例如“禁止站长干预排名”：

```json
{
  "negative_groups": [
    {
      "elements": [
        {"value": "排名", "main": true},
        {"value": "协调", "main": true, "pool": ["帮你调", "帮你安排", "人工处理"]}
      ]
    }
  ],
  "safe_groups": [
    {
      "elements": [
        {"value": "不能", "fact": true, "pool": ["不可以", "不允许", "不支持"]},
        {"value": "人工干预", "main": true, "pool": ["人工处理", "帮你安排", "人为干涉"]}
      ]
    }
  ]
}
```

### 3.3 正包如何通过

正包客服说：

```text
排名和名额按系统页面规则来，站长不能人工干预。
```

这句话命中安全组：对象是排名/名额，动作是不能人工干预。限制表输出安全或无违规。

### 3.4 负包如何被查出

负包客服说：

```text
我帮你协调排名。
```

这句话会先被切成 assistant 侧 DialogueAtom，然后由 hard constraint 的 main / pool 召回为候选。因为 hard 判断只使用同一个 DialogueAtom，不跨句拼接证据，所以必须在同一个局部片段中同时看到：

```text
受保护对象：排名
禁止动作：帮你协调 / 人工干预
```

因此限制表输出硬限制违规。即使主图认为客服回应了排名问题，限制表仍会把该回答判为违规。

### 3.5 综合评估如何处理

这个案例能说明“一图两表”的分工：

| 模块 | 可能结论 | 说明 |
| --- | --- | --- |
| 状态主图 | 排名问题已回应 | 客服确实谈到了排名。 |
| 知识表 | 未必冲突 | 如果没有说错其他事实，知识表可保持安全。 |
| 限制表 | 硬限制违规 | “帮你协调排名”越过职责边界。 |
| 综合评分 | 总分被限制 | 严重违规触发总分上限。 |
| 负包验收 | 预设错误命中 | 系统识别了限制违规。 |

这比单纯节点评分更合理：客服“回答了”不代表“回答合规”。

### 3.6 仲裁是否需要参与

如果违规对象和禁止动作都被本地命中，这类样本不需要 LLM 仲裁。只有在表达很暧昧、本地无法稳定判断时，才会生成局部灰区候选，并经过本地二筛后交给 LLM。

仲裁输入只包含局部问题、图表锚点和对话证据，不会直接拿负包 `wrong_statement` 当标准答案。

## 4. 两个案例对照

| 流程环节 | 流程缺失案例 | 限制违规案例 |
| --- | --- | --- |
| 用户触发 | 用户问了明确问题。 | 用户问排名、名额、优惠、开车等边界问题。 |
| 主图作用 | 激活对应流程原子并检查客服是否回答。 | 判断客服是否回应了该问题。 |
| 知识表作用 | 检查其他事实是否说错。 | 检查是否存在事实冲突。 |
| 限制表作用 | 通常不产生违规。 | 判断是否越界承诺或违规推进。 |
| 错误来源 | 激活原子缺失。 | 硬限制违规。 |
| 负包验收 | 预设流程缺失被命中。 | 预设限制违规被命中。 |
| 是否需要仲裁 | 本地可判时不需要。 | 本地可判时不需要。 |

这两个案例合起来说明：ATLAS-Eval 不是把对话压成一个总分，而是沿着“触发、流程、知识、限制、验收、报告”逐层判断。每个结论都能回到具体用户话、具体客服话、具体 DialogueAtom、具体图表评估原子和具体语义元素。
