# 03 双案例样本走读：沿评估流水线理解 SCEG 如何判断

本文档不是单纯展示“正包通过、负包识别”的效果，而是把 `02_METHOD_AND_MODULES.md` 中的方法流程落实到具体样本上，说明一条对话如何从原始 JSON 被一步步处理成评估报告。

为避免重复总方法，这里只保留与样本直接相关的流程。两个样本都来自飞毛腿骑手合同生效通知任务，对应离线图为：

```text
runs/graphs_offline/flyleg_rider_call_v1.json
```

对应示例报告可查看：

```text
runs/ridder_example/report_detail.html
runs/ridder_example/all_reports_merged.json
```

本文选择两个负包案例，并各自对照同编号正包：

| 案例 | 正包 | 负包 | 预设问题 | 讲解重点 |
| --- | --- | --- | --- | --- |
| 案例一 | `rider_11_positive` | `rider_11_negative` | 流程缺失 | 用户问“高峰要上线吗”，客服没有完成“午餐、晚餐高峰期需要上线”的 requirement。 |
| 案例二 | `rider_18_positive` | `rider_18_negative` | 限制违规 | 用户问排名和名额，客服说“我帮你协调排名”，违反“站长不能人工干预排名和名额”。 |

两个案例的价值不同：

- `rider_11` 说明系统如何识别“该说但没说”的流程漏项；
- `rider_18` 说明系统如何识别“流程说得差不多，但关键边界说错”的合规违规。

---

## 1. 先说明本文件采用的走读顺序

下面每个案例都按同一条评估流水线解释：

```text
样本输入
→ 读取离线 graph
→ Dialogue Loader 读取对话
→ Evidence Extractor 抽取证据单元
→ Evidence Matcher 匹配状态主图节点与 requirement
→ Knowledge Judge 核验知识副表
→ Constraint Judge 核验限制副表
→ Graph Evaluator 综合节点、关系、知识、限制和分数
→ Dataset Interface 做正负包验收
→ Local Second Filter 判断是否需要二次仲裁
→ Report Explainer 生成中文归因报告
```

也就是说，本文不再单独讲系统架构，而是看同一套流程如何落到两条具体对话上。

## 2. 案例一：流程缺失如何被定位——`rider_11_negative`

### 2.1 样本输入：这条负包故意破坏了哪个目标

`rider_11` 的场景是“提醒午餐晚餐高峰上线”。数据集中对这一组样本的设计是：

| 字段 | 内容 |
| --- | --- |
| 业务域 | rider |
| 场景 | 提醒午餐晚餐高峰上线 |
| 用户风格 | 强势 |
| 目标节点 | `explain_peak_online` |
| 目标 requirement | `peak` |
| 正包设计 | 明确说午餐和晚餐高峰期需要上线。 |
| 负包设计 | 完全不提午餐/晚餐高峰上线。 |
| 错误类型 | 流程缺失 |

因此，评估器不是泛泛判断“这段对话好不好”，而是要看：当用户触发高峰上线问题时，客服有没有命中图中的 `explain_peak_online / peak`。

### 2.2 读取离线 graph：这一目标在“一主图二副表”中的位置

离线图中，`explain_peak_online` 属于状态主图中的流程节点，不是知识副表或限制副表。

它的核心 requirement 是：

```text
peak：提醒骑手午餐和晚餐高峰期需要上线
```

对应 evidence group 的可执行证据条件大致是两类信息同时出现：

```text
1. 午餐 / 晚餐 / 高峰期 / 高峰
2. 上线 / 需要上线 / 要上线
```

所以，这个案例首先考察主图流程完成度：客服必须把“午餐、晚餐高峰期”和“需要上线”讲出来，不能只说“你自己看页面”。

### 2.3 Dialogue Loader：系统读入正负包原始对话

正包关键片段是：

```text
05 用户：高峰要上线吗？
06 客服：午餐、晚餐高峰期需要上线，这个时间段比较关键。
```

负包关键片段是：

```text
05 用户：高峰要上线吗？
06 客服：我先说其他规则，这点后面你自己看页面。
```

两条对话前面的业务语境相同，差别集中在客服是否正面回答高峰上线要求。

### 2.4 Evidence Extractor：把原始话术拆成可核验证据

进入评估时，系统会把每轮客服和用户话术整理成证据单元。对这个案例来说，关键证据不是整段对话，而是以下两类局部证据：

| 样本 | 候选证据 | 对 `peak` 的作用 |
| --- | --- | --- |
| 正包 | “午餐、晚餐高峰期需要上线” | 同时包含“午餐/晚餐/高峰期”和“需要上线”，可作为命中证据。 |
| 负包 | “我先说其他规则，这点后面你自己看页面” | 没有说明午餐、晚餐，也没有说明需要上线，不能作为命中证据。 |

这里体现了方法中的“结构化证据”思想：系统不是用整段相似度判断，而是把对话拆成可落到节点和 requirement 的证据。

### 2.5 Evidence Matcher：匹配状态主图节点

在正包中，`explain_peak_online` 节点被命中：

| 项目 | 正包结果 |
| --- | --- |
| 节点 | `explain_peak_online` / 高峰上线提醒 |
| 状态 | 已完成 |
| 首次命中轮次 | 第 6 句客服 |
| 命中原话 | “午餐、晚餐高峰期需要上线，这个时间段比较关键。” |
| requirement `peak` | 已完成 |

在负包中，同一个节点没有命中：

| 项目 | 负包结果 |
| --- | --- |
| 节点 | `explain_peak_online` / 高峰上线提醒 |
| 状态 | 缺失 |
| 首次命中轮次 | 无 |
| 命中原话 | 无 |
| requirement `peak` | 未完成 |

这里要强调一点：负包后面说了很多其他规则，例如单日合同、多日合同、排名规则、拒单取消超时、退出路径和额外奖励，但这些证据只能命中其他节点，不能替代 `peak`。

### 2.6 Knowledge Judge：知识副表没有把它误判成知识错误

`rider_11_negative` 中，客服说出的其他事实大体是正确的，例如：

```text
单日这类就是当天完成X单。
如果是多日合同，每天都要完成Y单。
报名排名按系统页面规则来。
如果出现拒单、取消、超时，都会影响资格。
退出需要在App的飞毛腿报名里取消；前一天Z点前取消，次日生效。
连续W天多日合同且每天Y单，才有额外奖励。
```

所以知识副表给出的结论是：已说出的事实没有明显冲突，知识分保持为 `100.0`。

这一步说明系统不会把所有低分都混成一个原因。`rider_11_negative` 的问题不是“说错知识”，而是“用户触发的流程节点没有完成”。

### 2.7 Constraint Judge：限制副表也没有发现越界承诺

这条负包没有说“我帮你保证名额”“站长可以帮你改排名”“我替你退出”之类的话，因此限制副表没有检出违规，限制分为 `100.0`。

这一步同样重要：它说明评估结果不是随便压分，而是把错误归因集中在主图流程缺失上。

### 2.8 Graph Evaluator：综合节点、关系和总体验收上限

由于 `explain_peak_online / peak` 缺失，主图上的流程完成度被明显拉低。报告中的核心分数为：

| 维度 | `rider_11_positive` | `rider_11_negative` | 说明 |
| --- | ---: | ---: | --- |
| 节点完成度 | 100.0 | 55.0 | 负包缺失高峰上线提醒节点。 |
| 结构关系分 | 97.6 | 55.0 | 主流程组不完整，并出现由缺失节点引发的前后关系问题。 |
| 知识分 | 100.0 | 100.0 | 已说出的业务事实没有明显冲突。 |
| 限制分 | 100.0 | 100.0 | 没有越界承诺。 |
| 总分 | 99.64 | 52.0 | 缺失核心履约证据后，触发总体验收上限机制。 |

这里的“总体验收上限机制”可以理解为：当核心流程证据缺失时，系统不会让其他正确内容把最终结果完全拉高。因为客服说了很多正确规则，但没有回答用户明确触发的高峰上线问题。

### 2.9 Dataset Interface：负包验收为什么是“本地通过”

`rider_11_negative` 是负包，因此报告里的“本地通过”不是说客服合格，而是说系统成功识别了负包预设错误。

验收结果中命中的预设错误为：

```text
error_family: flow_missing
node_id: explain_peak_online
requirement_id: peak
expected_detector: schema_executor
```

这说明评估器定位到了数据集希望它识别的问题：流程缺失发生在 `explain_peak_online / peak`，而不是泛泛地说“回答不好”。

### 2.10 Local Second Filter 与 LongCat 仲裁：核心错误不需要送审

这条样本中，核心错误已经由本地 schema executor 明确识别，所以不需要 LongCat 来判断“高峰上线有没有说”。

报告里虽然出现了一个关于“天气和订单量对资格帮助”的知识灰区候选，但本地二筛判断它属于低价值审计项，没有送 LongCat 仲裁。也就是说：

```text
高峰上线缺失 → 本地可判定 → 不依赖 LLM
天气帮助表述灰区 → 本地二筛忽略 → 不影响核心结论
```

### 2.11 Report Explainer：最终报告给评委看的归因

最终报告可以被解释为：

> 用户明确问“高峰要上线吗”，图中的高峰上线节点被激活；正包客服回答“午餐、晚餐高峰期需要上线”，所以 requirement 命中；负包客服说“后面你自己看页面”，没有提供午餐、晚餐高峰上线证据，因此节点缺失。知识和限制没有明显问题，所以报告把错误集中归因为流程缺失。

## 3. 案例二：限制违规如何被定位——`rider_18_negative`

### 3.1 样本输入：这条负包故意破坏了哪个目标

`rider_18` 的场景是“骑手问排名怎么来”。数据集中这一组样本的目标是：客服要说明排名和名额由系统页面规则决定，站长不能人工干预。

| 字段 | 内容 |
| --- | --- |
| 业务域 | rider |
| 场景 | 骑手问排名怎么来 |
| 用户风格 | 急躁 |
| 目标节点 | `explain_ranking_system` |
| 目标限制项 | `rider_no_manual_result` |
| 正包设计 | 说明飞毛腿报名按排名进行，并非站长干预。 |
| 负包设计 | 说站长可以帮他调排名。 |
| 错误类型 | 限制违规 |

和第一个案例不同，这里的重点不是“有没有说流程”，而是“说的时候有没有越过合规边界”。

### 3.2 读取离线 graph：这一目标在“一主图二副表”中的位置

`explain_ranking_system` 在状态主图中是“排名规则说明”节点；同时，`rider_no_manual_result` 在限制副表中是“禁止承诺排名结果”的限制项。

这体现了“一主图二副表”的配合方式：

| 层次 | 在本案例中的作用 |
| --- | --- |
| 状态主图 | 判断客服是否回应了排名、名额、系统规则这个流程点。 |
| 知识副表 | 判断单日、多日、退出、奖励等事实是否说错。 |
| 限制副表 | 判断客服是否承诺人工干预排名、名额或结果。 |

因此，这个案例会出现一个很关键的现象：主图节点可能被认为“有回应”，但限制副表仍然会判定“回应内容越界”。

### 3.3 Dialogue Loader：系统读入正负包原始对话

正包关键片段是：

```text
03 用户：报名和名额到底按什么排？
05 用户：排名到底谁定？
06 客服：名额和排名看系统页面规则，站长不能人工干预排名和名额。
```

负包关键片段是：

```text
03 用户：报名和名额到底按什么排？
05 用户：排名到底谁定？
08 客服：我帮你协调排名。
```

两条样本都触发了“排名和名额”这个问题，但正包给出安全口径，负包给出越界承诺。

### 3.4 Evidence Extractor：抽取两类不同性质的证据

在这个案例中，系统会抽取到两种证据：

| 证据类型 | 正包证据 | 负包证据 | 用途 |
| --- | --- | --- | --- |
| 主图流程证据 | “名额和排名看系统页面规则” | “我帮你协调排名” | 都与排名问题相关，会进入排名规则节点的匹配范围。 |
| 限制违规证据 | “站长不能人工干预排名和名额” | “我帮你协调排名” | 前者支持合规边界，后者触发禁止人工干预的限制项。 |

这一步说明：同一句话可以同时影响多个模块。比如“我帮你协调排名”既说明客服回应了排名问题，又触发了限制违规。

### 3.5 Evidence Matcher：状态主图先判断流程有没有回应

正包中，`explain_ranking_system` 节点被命中：

| 项目 | 正包结果 |
| --- | --- |
| 节点 | `explain_ranking_system` / 排名规则说明 |
| 状态 | 已完成 |
| 首次命中轮次 | 第 6 句客服 |
| 命中原话 | “名额和排名看系统页面规则，站长不能人工干预排名和名额。” |

负包中，这个节点也被视为有证据进入：

| 项目 | 负包结果 |
| --- | --- |
| 节点 | `explain_ranking_system` / 排名规则说明 |
| 状态 | 已完成 |
| 首次命中轮次 | 第 8 句客服 |
| 命中原话 | “我帮你协调排名。” |

这一点很适合向评委说明：主图节点命中不等于回答合格。主图先判断“是否回应了这个业务点”，而回答是否合规，要交给限制副表继续核验。

### 3.6 Knowledge Judge：知识副表没有发现事实冲突

`rider_18_negative` 后续仍然说了很多事实正确的内容：

```text
午餐、晚餐高峰期需要上线。
单日这类就是当天完成X单。
如果是多日合同，每天都要完成Y单。
拒单、取消、超时都会影响资格。
退出要在App的飞毛腿报名里取消，前一天Z点前取消，次日生效。
要拿额外奖励，需要连续W天多日合同且每天Y单。
```

因此，知识副表给出的知识分是 `100.0`。

这说明负包不是因为“业务知识全错”被识别，而是因为某一句越界承诺违反了限制副表。

### 3.7 Constraint Judge：限制副表定位到越界承诺

限制副表在 `rider_no_manual_result` 中检出违规：

| 项目 | 结果 |
| --- | --- |
| 限制编号 | `rider_no_manual_result` |
| 限制项 | 禁止承诺排名结果 |
| 结论 | 违规 |
| 证据原话 | “我帮你协调排名。” |
| 轮次 | 第 8 句客服 |
| 严重程度 | critical |
| 说明 | 命中 schema 化违例范围：受保护对象 + 禁止动作。 |

这里可以解释“受保护对象 + 禁止动作”的含义：

- 受保护对象：排名、名额、结果；
- 禁止动作：帮忙协调、人工干预、保证结果、优先处理。

负包中的“我帮你协调排名”同时包含“排名”和“帮你协调”，所以被限制副表识别为严重违规。

### 3.8 Graph Evaluator：综合后形成“流程高分、合规低分”的结果

`rider_18_negative` 很能说明 SCEG 为什么不能只看流程节点：

| 维度 | `rider_18_positive` | `rider_18_negative` | 说明 |
| --- | ---: | ---: | --- |
| 节点完成度 | 100.0 | 100.0 | 负包仍然覆盖了大部分流程节点。 |
| 结构关系分 | 97.6 | 97.6 | 主要结构基本完整，只存在轻微顺序扣分。 |
| 知识分 | 100.0 | 100.0 | 已说出的事实没有明显冲突。 |
| 限制分 | 100.0 | 38.0 | “我帮你协调排名”触发严重限制违规。 |
| 总分 | 99.64 | 42.0 | 严重违规触发总体验收上限机制。 |

这个分数结构非常适合说明方法：如果只看主图流程，负包似乎完成得不错；但限制副表会把边界错误单独拉出来，最终让总分下降。

### 3.9 Dataset Interface：负包验收为什么是“本地通过”

负包验收命中的预设错误为：

```text
error_family: constraint_violation
node_id: explain_ranking_system
constraint_id: rider_no_manual_result
evidence_span: 我帮你协调排名。
expected_detector: schema_executor
```

这说明系统不仅发现“有违规”，还把违规定位到了具体节点、具体限制项和具体原话。

### 3.10 Local Second Filter 与 LongCat 仲裁：核心违规不需要 LLM 才能判断

这条样本的核心违规由本地限制副表直接识别，不需要 LongCat 判断。

报告中同样存在一个“天气和订单量对资格帮助”的低价值知识灰区候选，但本地二筛没有送审，因为它没有产生冲突或违规，不影响 `rider_no_manual_result` 这个核心结论。

因此本案例体现的是：

```text
排名越界承诺 → 本地限制副表可判定 → 不依赖 LLM
其他低价值灰区 → 本地二筛过滤 → 避免过量仲裁
```

### 3.11 Report Explainer：最终报告给评委看的归因

最终报告可以被解释为：

> 用户问“报名和名额到底按什么排”“排名到底谁定”，这会触发排名规则相关节点。正包客服回答“看系统页面规则，站长不能人工干预”，所以流程和限制都合格。负包客服回答“我帮你协调排名”，虽然它回应了排名问题，也继续说完了高峰、单日、多日、退出和奖励等流程，但这句话违反了“禁止承诺人工干预排名结果”的限制项，所以限制分下降，并通过总体验收上限影响最终总分。

## 4. 两个案例放在同一条流程里对照

| 流程环节 | `rider_11_negative`：流程缺失 | `rider_18_negative`：限制违规 |
| --- | --- | --- |
| 样本输入 | 预设错误是 `flow_missing`。 | 预设错误是 `constraint_violation`。 |
| 图中锚点 | 主图节点 `explain_peak_online`，requirement `peak`。 | 主图节点 `explain_ranking_system`，限制项 `rider_no_manual_result`。 |
| 用户触发 | 用户问“高峰要上线吗？” | 用户问“报名和名额到底按什么排？”“排名到底谁定？” |
| 关键客服原话 | “这点后面你自己看页面。” | “我帮你协调排名。” |
| Evidence Matcher | 找不到“午餐/晚餐高峰期需要上线”的命中证据。 | 能找到排名相关回应，因此主图节点仍被命中。 |
| Knowledge Judge | 其他事实基本正确，知识分 100.0。 | 其他事实基本正确，知识分 100.0。 |
| Constraint Judge | 未发现越界承诺，限制分 100.0。 | 命中严重违规，限制分 38.0。 |
| Graph Evaluator | 节点完成度 55.0，总分 52.0。 | 节点完成度 100.0，但总分 42.0。 |
| 负包验收 | 命中 `flow_missing / explain_peak_online / peak`。 | 命中 `constraint_violation / rider_no_manual_result`。 |
| 是否依赖 LongCat | 核心错误本地可判定。 | 核心错误本地可判定。 |
| 报告归因 | 该回答的高峰上线节点没有回答。 | 回答了排名问题，但越过职责边界。 |

这两个案例合起来，能帮助评委理解：SCEG 不是简单把对话打成一个分数，而是沿着主图和副表分层判断。

- 主图负责判断流程有没有被完成；
- 知识副表负责判断已说出的事实有没有冲突；
- 限制副表负责判断有没有越界承诺；
- 综合评分和总体验收上限负责把严重问题反映到最终结果；
- 正负包验收负责确认系统是否真的识别到了预设错误；
- 本地二筛负责避免把低价值灰区都送给 LongCat。

## 5. 答辩

> 03 里我们不是为了单纯展示效果，而是把两个样本沿着 02 的方法流程跑一遍。第一个样本中，用户问“高峰要上线吗”，这会激活主图里的高峰上线节点。正包客服说“午餐、晚餐高峰期需要上线”，所以 evidence group 命中；负包客服说“后面你自己看页面”，没有形成这个节点的证据，因此主图判定流程缺失。知识副表和限制副表没有发现其他错误，所以报告把问题集中归因为流程缺失。第二个样本中，用户问排名和名额，负包客服说“我帮你协调排名”。这句话在主图上确实回应了排名问题，但在限制副表中触发了“禁止人工干预排名结果”的违规项。因此节点完成度可以很高，限制分却很低。
